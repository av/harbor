### [Harbor (Agent Evaluations)](https://github.com/harbor-framework/harbor)

> Handle: `harbor-agent-evals`<br/>
> Interface: CLI, no published port

[Harbor Framework](https://docs.harborframework.com/) is the agent evaluation framework from the creators of Terminal-Bench. Its former `laude-institute/harbor` repository redirects to `harbor-framework/harbor`. It runs tasks, agents and verifiers in container environments, including local Docker.

![Terminal transcript of the tiny local agent evaluation run](./harbor-harbor-agent-evals.png)

The handle **`harbor-agent-evals`** keeps the framework's Harbor name and makes its agent-evaluation purpose explicit. Harbor's existing short command `h` manages the service. An opt-in command wrapper, also named `harbor-agent-evals`, runs its commands:

```bash
h up harbor-agent-evals
harbor-agent-evals run --path hello --agent oracle --job-name smoke
```

`h` is the toolkit's standard short alias. `harbor-agent-evals` is a launcher into the container, not another installation of the upstream CLI. The engine's own `harbor` binary stays inside the container. Existing named Promptfoo evaluations and the built-in Harbor Bench service are unchanged.

The full spelling `harbor up harbor-agent-evals` also works. It necessarily contains Harbor twice because both the toolkit and service have that name. The preferred commands above avoid that repetition without renaming either project.

## Starting

This service uses your local Docker daemon. If the toolkit's standard `h` alias is missing, install it with:

```bash
harbor ln --short
```

On Linux, give the runner the socket's group ID:

```bash
h config set HARBOR_HARBOR_AGENT_EVALS_DOCKER_GID "$(stat -c %g /var/run/docker.sock)"
```

For a socket owned by group ID `0`, keep the default. The socket must be available at `/var/run/docker.sock`.

Create the workspace as your host user before starting:

```bash
mkdir -p "$(h home)/services/harbor-agent-evals/data"
h build harbor-agent-evals
h wrappers add harbor-agent-evals
h up harbor-agent-evals
harbor-agent-evals --help
harbor-agent-evals run --help
harbor-agent-evals --version
```

`up` keeps an idle runner available for `harbor exec` and `harbor shell`. Each `harbor-agent-evals` invocation runs a temporary container with the same workspace and removes it on exit. It also works without starting the idle runner first. There is no web server or `--open` action.

## Usage

### Tiny free local evaluation

The included task asks an agent to write a greeting. The upstream `oracle` agent executes the included solution and the verifier checks the resulting file. This validates task setup, execution, verification and result persistence. It measures harness operation, not model quality. It uses no model, API key or cloud provider.

```bash
cp -R "$(h home)/services/harbor-agent-evals/example" \
  "$(h home)/services/harbor-agent-evals/data/hello"
harbor-agent-evals run --path hello --agent oracle --env docker \
  --n-concurrent 1 --n-attempts 1 --job-name hello-oracle
harbor-agent-evals results hello-oracle
```

Expect one completed trial, zero errors and reward `1.0`. Results, verifier logs and the job configuration appear under `services/harbor-agent-evals/data/jobs/hello-oracle/`. Use a fresh job name for each run. With a custom workspace, copy the task there instead.

To evaluate a model, replace `oracle` with an upstream agent and supply that agent's model and endpoint settings. Credentials can be configured in `h env harbor-agent-evals`; they are passed to the runner. Agent-specific options and environment forwarding are documented by `harbor-agent-evals run --help`. Paid providers are optional.

### Commands

```bash
harbor-agent-evals datasets list
```

Keep local tasks, configs and results inside the mounted workspace. Absolute paths outside it exist only on the host unless separately mounted. Dataset downloads and job outputs use the workspace by default. Tasks create separate Docker containers and networks, so these do not automatically join the toolkit's `harbor-network` or inherit its backend service names.

### Command wrapper

`h wrappers add harbor-agent-evals` uses Harbor's existing command-wrapper feature. It creates a link in the configured `cli.path` (normally `~/.local/bin`), refuses to replace or shadow another command, and is optional outside the preferred workflow. Remove it with `h wrappers rm harbor-agent-evals`.

If the launcher is not found, check that `cli.path` is on your shell's `PATH`, then run `h wrappers sync`. No Python package is installed on the host by this step.

### Read saved results

```bash
harbor-agent-evals results hello-oracle
```

`results` reads `jobs/<name>/result.json` from the workspace and prints completed trials, errors and mean reward. A job is a named evaluation run. Reading results makes no model or hosted-service call. An unknown job reports an error and exits with status 2. This wrapper command supplements the framework's own subcommands, including `run`, `datasets`, `job` and `task`. The upstream `view` subcommand starts a server inside the container and needs an explicit port mapping and `--host 0.0.0.0` for browser access; use `results` for the CLI workflow.

## Configuration

### Environment Variables

Set these with [`harbor config`](./3.-Harbor-CLI-Reference.md#harbor-config):

| Variable | Default | Purpose |
| --- | --- | --- |
| `HARBOR_HARBOR_AGENT_EVALS_VERSION` | `0.24.0` | Upstream PyPI package version. Rebuild after changing it. |
| `HARBOR_HARBOR_AGENT_EVALS_WORKSPACE` | `${HARBOR_HOME_VOLUME}/services/harbor-agent-evals/data` | Absolute workspace path, identical on host and runner. Create it as your host user. |
| `HARBOR_HARBOR_AGENT_EVALS_DOCKER_GID` | `0` | Supplementary group for access to the host Docker socket. |

For example:

```bash
h config set HARBOR_HARBOR_AGENT_EVALS_WORKSPACE /absolute/path/to/evals
mkdir -p /absolute/path/to/evals
h up harbor-agent-evals
```

The runner uses Harbor's host user and group IDs. Its home is the workspace, so tasks, results, downloaded datasets and the upstream cache persist there. Upstream telemetry is disabled with `HARBOR_TELEMETRY=0`.

### Volumes

- The workspace is mounted at **the same absolute path** in the runner and on the host. The upstream harness asks the host daemon to bind job log directories into task containers, so translating it to `/app` would break verification and results.
- `/var/run/docker.sock` grants control over the host Docker daemon. Only run trusted tasks and agents on a host whose Docker access you intend to grant.
- The workspace uses a shared SELinux label (`:z`). The runner disables its own SELinux label isolation to access the Docker socket on Fedora. Upstream task log mounts also use shared labels.
- The build installs Git, Python, Docker CLI, Docker Compose and the pinned `harbor` package. No privileged Docker-in-Docker daemon or paid sandbox is required.

## Troubleshooting

- **Socket permission denied:** set `HARBOR_HARBOR_AGENT_EVALS_DOCKER_GID` using the Linux command above, then recreate the runner with `h up harbor-agent-evals`.
- **Workspace permission denied:** create the workspace as your host user before the first run. If Docker already created a root-owned directory, correct its ownership before retrying.
- **Missing reward or empty result directories:** ensure the workspace is an absolute path and matches on both sides of the mount. Do not put results outside it.
- **Docker unavailable:** Docker Engine or Docker Desktop must be running, with its socket exposed at `/var/run/docker.sock`.
- **Duplicate job name:** choose another `--job-name` rather than overwriting an existing run.

```bash
h logs harbor-agent-evals --no-follow
h down harbor-agent-evals
```

The idle runner has no application logs. Evaluation output appears in the invoking terminal and workspace job logs. Stopping the runner retains jobs and task inputs. Interrupted evaluations may leave upstream task containers for inspection or cleanup.
